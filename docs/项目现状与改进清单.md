## 一、项目定位

一个 6 人宿舍的**电费余量估算与断电预警**工具。不做「实时监控」，因为数据源不存在：

- 学校 i 太湖「缴电费」只覆盖 **1–9 号楼**，本项目所在 **19 号楼**不在范围；
- 宿管**每 7 天手抄一次**，无电子接口；
- 宿舍禁用大功率电器、禁止私改电路，加装采集器不可行。

因此产品形态固定为：**人工抄表（7 天一次）+ 日均模型推算 + 阈值推送**。

线上地址：`https://dorm-power-ledger.app.workbuddy.host/?sharecode=JW4LBH45CN`

## 二、当前实现

### 2.1 技术栈

| 层 | 选型 | 说明 |

### 2.3 接口契约

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/` | — | 返回 HTML，**内嵌首屏数据** `window.__BOOT__` |
| GET | `/api/state` | — | 按身份返回 owner / guest / setup 三种结构 |
| POST | `/api/login` | — | 管理员登录；`ownerKey` 为空时即"首次设置口令" |
| POST | `/api/guest-login` | — | 舍友登录，校验 `guestKey`；未设置时 `open:true` 直接放行 |
| POST | `/api/change-key` | 管理员 | 改管理口令（≥4 位） |
| POST | `/api/set-guest-key` | 管理员 | 设/清舍友口令 |
| POST | `/api/reading` | 管理员 或 舍友口令 | 记读数，支持 `date:"YYYY-MM-DD"` 补录 |
| POST | `/api/charge` | 同上 | 记充值 |
| DELETE | `/api/record/:id` | 管理员 | 删记录 |
| POST | `/api/settings` | 管理员 | room / threshold / people / pushToken |
| POST | `/api/reset` | 管理员 | 清空记录 |
| POST | `/api/push-test` | 管理员 | 发测试推送 |
| POST | `/api/push-now` | 管理员 | 立即推送 |
| GET/POST | `/api/cron?secret=` | cronSecret | 外部定时触发推送（可唤醒休眠容器） |
| GET | `/api/export?format=json\|csv` | 管理员 | 导出全部状态；加 `&secret=0` 脱敏 |
| POST | `/api/import` | 管理员（**空库免鉴权**） | 从导出文件恢复，覆盖前另存 `.bak.import` |

### 2.4 数据模型（data.json）

```json
{
  "room": "19#-411",
  "threshold": 88,
  "people": 6,
  "pushToken": "<PushPlus token>",
  "lastPushDate": "2026-10-28",
  "ownerKey": "<明文管理口令>",
  "guestKey": "<明文舍友口令>",
  "logs": [{ "ts": 0, "action": "录读数", "detail": "542.0 度（2026-11-01）", "who": "管理员", "ok": null }],
  "records": [
    { "id": 1, "type": "reading", "value": 654.0, "ts": 0, "who": "充值后抄表" },
    { "id": 2, "type": "charge",  "value": 654.0, "ts": 0, "who": "360元 / 0.55元一度" },
    { "id": 3, "type": "reading", "value": 528.0, "ts": 0, "who": "抄表" }
  ]
}
```

- `type` 只有 `reading`（电表剩余电量）与 `charge`（充值度数，仅备注，不参与计算）；
- `ts` 为毫秒时间戳，由 `date` 参数解析为当日 12:00，或默认 `Date.now()`。

### 2.5 核心算法（`stats()` + `estimate()`）

```
日均 = (最早读数 − 最近读数) ÷ 相隔天数        // 仅当 days ≥ 0.2 且 used > 0
估算余量 = 最近读数 − 日均 × 距最近读数天数    // 下限 0
预计可用天数 = 估算余量 ÷ 日均
预计断电时刻 = now + 预计可用天数 × 86400000
```

### 2.6 权限模型（服务端强制）

| 角色 | 判定 | 可见 | 可写 |
|---|---|---|---|
| 管理员 | `x-owner-key` == `ownerKey` | 完整 `ownerState`（明细、日均、断电日期） | 全部 |
| 舍友 | `x-guest-key` == `guestKey` | `publicState`（**取整余量、取整天数，无 records**） | 仅 reading / charge |
| 未登录 | 无 key | `setup`（未设口令时）或 `guest` | 无 |

取整规则：余量 ≤20 度取整，>20 度按 5 度取整；天数取整，≥100 显示 `99+`。

## 三、业务约束（不可违背）

来自《需求访谈与设计前提.md》，改代码前必读：

1. **数据粒度 7 天**，任何"实时"需求在此前提下不成立；
2. **预警窗口 7 天**（跑卡务中心 1 天 + 周末不办 + 缓冲），阈值 = 日均 × 7 = 88 度；
3. **断电不可逆**：老宿舍无线上缴费，断电当晚无补救 → 宁可误报，不可漏报；
4. **不做**：实时采集、加装电表、账单分摊/催缴、微信小程序（原因见文档）。

当前实测口径：日均 **12.6 度/天**（654 → 528，10 天）；6 人分摊 2.1 度/人/天。

## 五、改进清单（可直接派任务）

> 每条含**验收标准**，改完应能用 `curl` 或页面验证。P0 优先做，P3 明确不做。

### P0 — 数据正确性与安全（建议先做这 3 条）

**P0-1 录入幂等** —— ✅ **v1.1 已完成**（`server.js` 同日重复 / 读数上升 / 偏离 40% 三种 409，`force:true` 才落库），本节保留备查，**无需再做**。
- 需求：同一 `type + value + 日期(YYYY-MM-DD)` 视为重复，拒绝写入或返回已存在记录；
- 验收：连续两次 `POST /api/reading {"value":528,"date":"2026-10-28"}`，第二次返回 `409` 或 `{ok:true, dup:true}`，`records` 长度不变。

**P0-2 口令哈希化**
- 需求：用 `crypto.scrypt`（Node 内置，零依赖）存储 `ownerKeyHash` / `guestKeyHash` + 随机 salt；比对改为哈希比较；
- 兼容：读取旧 `ownerKey` 明文时自动升级为哈希并清除明文；
- 验收：`data.json` 中不再出现明文口令；原口令仍可登录。

**P0-3 数据导出与备份** —— ✅ **v1.2 已完成**，并补了原需求没写的东西：导入（否则备份没法回灌）、空库免鉴权导入（否则升级后恢复路径死锁）、启动自检（`.bak` 自动捞回）、`PUSH_TOKEN` 环境变量（token 不再随库丢）。
- 需求：`GET /api/export?format=csv|json`（管理员），导出全部记录；服务端每日首次写入前生成 `data.json.bak`；
- 验收：导出文件能被 Excel 打开，字段 `日期,类型,数值,记录人`。

### P1 — 体验与预测精度

**P1-1 预测模型对比（最有简历价值）**
- 需求：实现三种日预测——全程平均、7 天滑动平均、指数平滑（α=0.3）；加 `GET /api/backtest` 用历史读数做**留一法**回测，输出各自 MAPE；页面展示对比表，允许管理员切换当前模型；
- 验收：返回 `[{model:"mean", mape:8.2}, ...]`，与手工计算一致。

**P1-2 抄表提醒**
- 需求：若 `距最近读数 > 8 天`，推送文案追加一行「已 X 天未抄表，估算误差可能 >15%，建议校准」；
- 验收：把某条读数日期改到 9 天前，`/api/push-test` 文案含该提示。

**P1-3 周末保护**
- 需求：周五 18:00 若「预计可用天数 ≤ 9」，额外推一条「周末卡务中心不办公，建议今天充值」；
- 验收：构造余量 100 度、周五时间点，触发两条推送。

**P1-4 记录编辑**
- 需求：`PATCH /api/record/:id`（管理员）允许改 `value`，用于录入错误修正（现在只能删了重录）；
- 验收：改完 `stats()` 结果随之变化。

**P1-5 多 token 推送**
- 需求：`pushToken` 支持数组，6 人各自填；推送时遍历，单个失败不影响其他；
- 验收：配置两个 token（其中一个无效），返回 `{ok:1, fail:1, detail:[...]}`。

## 六、验证方式（每次改完必做）

1. 本地 `node server.js`，浏览器开 `http://localhost:3000`；
2. 三个视角各点一遍：未登录（setup）、舍友（guest）、管理员（owner）；
3. `curl` 验权限边界：
   - 无口令 `POST /api/settings` → 403/428；
   - 带 `x-owner-key` → 200；
4. 发布前**先把线上 `data.json` 拉回本地**，避免覆盖真实记录（真实数据只有一份，在服务器上）。
